# AirMe 決賽需求基準

> 基準日期：2026-07-16｜產品：單一個人 AirMe｜平台：iOS、Android、Web

## 產品目標

使用者描述活動情境後，AirMe 結合具來源與時間的環境資料、最低限度個人條件及版本化官方規則，產生固定格式、可解釋、能安全追問的行動卡。

## P0 功能需求

| ID | 需求 | 成功結果 |
|---|---|---|
| R-01 | 單一跨平台 client | 同一 Expo 專案輸出 iOS、Android、Web，相同流程與資料語意 |
| R-02 | 輸入式本機個人檔案 | 一句話轉成年齡群、最多三個敏感標籤、通勤、活動與粗略地點；只保存受控欄位，原始描述不保存 |
| R-03 | 活動理解確認 | 接受 2–800 字活動描述，先顯示活動、時間、地點、強度、時長、當下狀況與目標；缺資料只問一題，確認後才送推薦 |
| R-04 | 環境資料 | 標準化 AQI、主要污染物、天氣、來源、觀測時間、取得時間與 stale 狀態 |
| R-05 | 官方底線 | AQI、敏感條件、強度、資料缺失／過期共同決定不可降低的風險層級 |
| R-06 | AI 行動卡 | 量界智算／fixture 只能輸出符合 schema 的風險、標題、時間、地點、強度、裝備、理由與安全提醒 |
| R-07 | 安全追問 | 只回答原情境內空品、活動安全與一般自我保護；其他固定拒答 |
| R-08 | Air 日誌 | 最多 20 筆活動／環境／建議摘要與 50 筆回饋以 recommendation ID 整合；可全部清除且不保存 currentCondition |
| R-09 | 可重播備援 | 沒有網路或外部服務時仍能展示完整流程，並清楚標示 fixture／非即時 AI |
| R-10 | API 邊界 | 所有秘密與外部呼叫只在 Coolify API 後端，公開錯誤不含 provider 細節 |
| R-11 | 安全路線交接 | 起終點、時間與方式不持久化；未配置 route provider 時顯示資料不足，只由使用者主動開啟外部地圖 |

## 安全與隱私需求

- 不蒐集姓名、學號、學校、聯絡方式、病歷、精確住址或長期 GPS 軌跡。
- 新持久化座標四捨五入到小數二位，API 舊資料相容上限三位且只接受臺灣服務範圍；後端只接收當次推論必要內容。
- 不診斷、不建議藥物、不判定症狀成因、不保證活動安全。
- 緊急描述停止一般建議，提示停止活動、告知成人與尋求當地緊急協助。
- 官方規則由程式執行；模型輸出風險只能相同或更保守。
- 真實 key、token、憑證、個資、合約與內部文件不得進入版本控制、bundle、log 或文件。

## 非功能需求

- Request／response 必須通過共用 Zod schema。
- 外部服務具 timeout、資料新鮮度、cache／fallback 與可理解錯誤。
- UI 支援手機與桌面、固定淺綠白亮色主題、鍵盤 focus、足夠對比與至少 44pt 觸控目標；AQI 風險色保留語意。
- 核心流程須可由自動化測試與 30 個固定安全案例重播。
- Live、partial、stale、fixture provenance 必須在資料和畫面上可辨識。

## 不在 P0

教師端、班級統計、正式登入與跨裝置同步、雲端個人資料庫、即時 route provider／完整導航／街道級污染路線、Line Bot、推播、Power BI、健康中心串接、醫療預測或個人敏感閾值模型。

## 外部決策與限制

- 量界智算 model ID、額度、rate limit、JSON 相容性由團隊帳號確認。
- 競賽官方的「概念驗證（Azure）」25% 與指定雲端平台要求尚未取得 Coolify／量界書面例外；無例外時核心驗證必須使用主辦指定資源。
- VPS、Coolify 與 PostgreSQL 為團隊管理環境；未經 owner 允許不建立、修改或刪除其他專案資源。
- Mobile 最終交付形式與團隊發布／監控／回滾 owner 尚未決定。
