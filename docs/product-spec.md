# AirMe 決賽版產品規格

> 狀態：2026-07-16 已核准並實作的決賽產品基準
> 產品：單一個人 AirMe，輸出 App 與 Web
> 決賽日期：2026-07-26
> 定位：受約束、可解釋的個人空氣健康 AI 行動助理

## 1. 文件用途與判斷原則

本文件整合海選創意構想、複選提案簡報、主辦方課程與評審回饋，以及後續團隊討論。原始材料的時間與目的不同，因此採以下原則判斷：

1. 使用者最新確認的方向優先於早期提案。
2. 比賽規則與可驗證事實優先於宣傳性文案。
3. 群組討論用來辨認修改方向，不逐句複製，也不把未確認想法視為需求。
4. 沒有資料、模型、權限或時間證據的能力列為未來方向，不放入決賽 P0。
5. 功能必須共同證明一個 AI 核心，不以服務或頁面數量堆疊完整度。

## 2. 競賽脈絡

第六屆中學生黑客松主題為「生活化人工智慧加值雲端應用」。決賽不能只展示大數據儀表板，也不能在傳統 App 上附加一個通用聊天視窗。

目前掌握的決賽評分重點：

| 項目 | 比例 | AirMe 必須證明的事 |
|---|---:|---|
| 問題理解度 | 10% | 使用者已看得到空品，但仍難以把環境、個人與活動轉成當下選擇 |
| 創新性 | 10% | AI 理解活動意圖，組合真實情境並產生不同而合理的個人行動方案 |
| 企劃完整度 | 20% | 範圍、資料、AI 邊界、隱私、錯誤、驗收與未來方向一致 |
| 概念驗證（Azure） | 25% | 依官方簡章，使用主辦單位指定的雲端平台證明一段可操作的 AI 核心流程，並可說明輸入、處理、依據與輸出 |
| 簡報表達 | 35% | 用真實故事和穩定 Demo 讓評審快速理解 AirMe 的不可替代性 |

評審已明確關注「AI 不足」與「AI 助理如何不跑題」。因此 AI 安全、固定輸出、拒答與測試不是附錄，而是產品功能。

目前 repository 的產品部署方向是 Coolify／量界智算，與官方簡章的 Azure 計分文字不一致。在取得主辦單位或指導老師可以提供的書面許可前，不得把 Coolify／量界流程宣稱為已完成官方 Azure 概念驗證；若無例外，需恢復 Azure／主辦指定資源的核心驗證路徑，Coolify 可繼續作為產品展示入口。

## 3. 問題定義

現有官方與民間工具已能提供 AQI、污染物、預報、常用地點與通用活動建議。AirMe 不應聲稱其他 App 只有數字或完全沒有個人化。

仍存在的具體缺口是：

> 使用者收到環境資訊後，仍需自行組合「我現在想做的活動、活動強度、時間地點、個人敏感條件與當下狀況」，才能決定是否照常、調整、改地點或停止。

對中學生而言，這會出現在騎車上學、體育課、放學運動、社團與校外活動。相同 AQI 對一般學生的短時間步行與敏感學生的長時間劇烈運動，意義不相同。

## 4. 核心使用者

第一核心使用者是有通勤、體育課或戶外活動需求的中學生，尤其是自述有過敏、氣喘、鼻炎或對空品較敏感者。

代表人物「阿翔」：15 歲、騎車通勤、喜歡戶外活動、有過敏性鼻炎。他不是想研究空品圖表，而是想知道：「今天下午跑 1600 公尺，我需要怎麼調整？」

AirMe 是個人產品。老師、家長或一般使用者可以用同一套個人流程，但決賽不建立教師端、班級端、角色權限或匿名班級統計。

## 5. 產品定義

### 5.1 一句話

> AirMe 理解你現在想做什麼，結合即時空氣、天氣、最低限度個人敏感條件與官方準則，透過量界智算 AI 產生有依據、可解釋、能追問且知道何時拒答的個人行動方案。

### 5.2 不是什麼

- 不是醫療診斷、症狀成因判定或醫療裝置。
- 不是 AQI、天氣與健康圖表的集合。
- 不是能回答任何問題的聊天機器人。
- 不是已有成熟預測模型的健康風險系統。
- 不是學生監控、班級病歷或學校決策系統。
- 不是把越多雲端服務放進架構圖就越好的展示。

### 5.3 App 與 Web

App 與 Web 是相同 AirMe 的不同輸出：

- 相同個人設定、活動輸入、行動卡、追問與回饋。
- 相同 API、AI 核心、資料格式與安全政策。
- 手機強調快速輸入與隨身閱讀；Web 強調鍵盤輸入、較寬版內容及穩定展示。
- 不依平台決定使用者身分，不建立教師 Web。

## 6. 核心循環

1. 使用者免登入，以一句話建立只在裝置端的最低限度個人情境；確認後只保存受控欄位，不保存原始自我描述。
2. 使用者說明活動，例如「明天下午要跑 1600 公尺，我今天鼻子很塞」。
3. AirMe 擷取活動、時間、地點、強度、時長與當下狀況，先顯示「我理解的是」；必要資料不足時只問一個最重要問題。
4. 使用者確認結構化理解後，後端取得最新環境資料並確認資料新鮮度。
5. 官方規則產生不可突破的安全底線。
6. 量界智算組合情境，產生固定格式行動卡。
7. 後端驗證 Schema、資料引用、醫療界線與內容過濾結果。
8. 使用者查看「怎麼做、為什麼、使用哪些資料、何時停止」。
9. 使用者可在原情境內追問替代方案。
10. 活動後回報是否不適與建議是否有幫助；活動、環境、建議與回饋整合成裝置端 Air 日誌。

## 7. P0 功能與畫面

### 7.1 初次設定

- 使用者以一句話描述年齡、敏感狀態、通勤、常見活動與常用區域；AirMe 顯示受控欄位供確認。
- 可選裝置暱稱不要求真名、不傳後端；不建立 Email／密碼或雲端帳號。
- 已知競賽區域可轉成粗略座標；其他臺灣區域由使用者輸入名稱與座標，新資料持久化前四捨五入到二位小數，API 為舊資料相容最多接受三位。
- 明確說明資料用途、非醫療定位與裝置端保存。
- 原始自由描述只存在表單記憶體，確認後不持久化；資料不足時明確要求補充，不自行猜測。

### 7.2 今日頁

- 第一視覺焦點是「你今天想做什麼？」而不是圖表。
- 顯示目前位置／選定地區、AQI、主要污染物、資料時間與簡短環境摘要。
- 提供自然語言輸入；結構化理解確認取代大量固定選項。
- 可返回修改活動文字；缺少活動或時長時只顯示一個澄清輸入。

### 7.3 AI 行動卡

每張行動卡至少包含：

1. 建議等級：照常、調整、避免／延期、資料不足。
2. 一句話結論。
3. 具體行動：降低強度、縮短時間、改室內、增加休息、使用一般防護、告知家長／老師等。
4. 替代方案。
5. 使用事實：活動、時間、地點、AQI、主要污染物、資料時間、明示的個人條件。
6. 理由：環境、活動與個人條件如何共同影響建議。
7. 停止條件與求助提示。
8. 資料來源與非醫療聲明。
9. 可追問選項。

### 7.4 限定領域追問

允許：

- 為什麼得到這個建議。
- 改成室內、降低強度、換時間或地點後是否不同。
- 一般曝露降低與活動安全做法。
- 如何把建議簡短轉述給家長或老師。

拒絕或升級：

- 作業、娛樂、一般聊天等離題要求。
- 要求忽略規則或改變系統身分。
- 疾病診斷、藥物劑量、治療或保證安全。
- 嚴重症狀或緊急危險；應提示停止活動並尋求成人或專業協助。

### 7.5 五秒回饋

- 是否進行活動。
- 活動後是否不舒服：無、輕微、明顯、不想回答。
- 建議是否有幫助。
- 可選短註記。

決賽版只把回饋視為使用者自述歷史，不宣稱症狀由空污造成，也不產生「鼻塞機率提高 78%」等無資料依據的數字。

### 7.6 Air 日誌

- 每筆日誌整合去識別化活動摘要、當時 AQI／天氣、建議摘要、規則版本與活動後回饋。
- 日誌不保存個人描述原稿、完整活動文字、`currentCondition`、context token 或模型對話。
- 舊 version 1 本機資料 migration 後保留既有摘要；沒有當時環境的舊資料顯示「當時環境細節未保存」，不補造數值。

### 7.7 通勤與戶外時間

- 使用者輸入起點、終點、時間與方式；這些輸入不持久化、不傳 AirMe API。
- 顯示出發地環境判斷，並由使用者明示點擊後開啟外部地圖。
- 尚未連接可信 route provider，因此距離、時間與戶外區段交由外部地圖確認，AirMe 明確顯示資料不足。
- 禁止使用「最低污染」「最安全」或沒有研究依據的健康分數。

### 7.8 示範與錯誤狀態

- 定位拒絕：允許手動選地區。
- AQI／天氣資料失敗：顯示失敗來源與時間，不用舊資料冒充最新資料。
- 量界智算 AI 逾時／限流：提供重試；現場可切換清楚標示的本機示範情境。
- Structured Output 驗證失敗：不顯示原始模型文字，改回安全錯誤狀態。
- 完全離線：只能展示預先準備並標示時間與情境的資料，不能宣稱 AI 線上流程正在運作。

## 8. AI 不可替代的能力

### 8.1 意圖結構化

從自然語言擷取 activity、time、location、intensity、duration、currentCondition 與 userGoal，必要欄位不完整時只問一個最重要的補充問題。

### 8.2 情境組合

同時使用活動、個人標籤、即時環境、天氣、官方規則與使用者明示的歷史回饋。Demo 必須證明相同 AQI 下改變個人條件或活動強度會產生合理不同結果。

### 8.3 可解釋生成

模型不是回傳自由文章，而是符合 JSON Schema 的行動卡；每項理由只能引用請求中存在的事實與核准規則。

### 8.4 對話延續

追問使用原 request ID 對應的已驗證情境，不重新讓模型猜測地點、AQI、病史或使用者身分。

## 9. 安全原則

- 官方門檻由程式規則決定，AI 不能覆寫。
- 模型看不到 secret，也不能直接呼叫任意網路工具。
- 不足資料明確標示；禁止補造位置、環境值、症狀或未來反應。
- 不使用「保證安全」「一定是空污造成」等語句。
- 不蒐集姓名、生日、學號、學校、病歷、精確住址等 P0 非必要資料。
- 個人設定和回饋預設在裝置端；後端按請求處理，不建立個人病歷資料庫。
- 技術 log 不含完整提示、症狀、精確位置或完整模型輸出。

詳細測試矩陣見 [AI 安全與評估](ai-safety-and-evaluation.md)。

## 10. 驗收標準

### 10.1 主要流程

- App 和 Web 都能完成設定、輸入、取得行動卡、追問與回饋。
- 同一 API 契約可服務 App 與 Web。
- 線上 Demo 的推薦請求實際經過 Coolify API 與量界智算。
- 行動卡顯示資料來源、資料時間、使用事實與非醫療聲明。

### 10.2 AI 真實性

- 至少三組相同環境、不同個人／活動條件的對照結果。
- 至少一個必要資料不足時的澄清或保守回應。
- 所有成功結果通過 JSON Schema 驗證。
- 不允許以前端寫死結果冒充即時模型輸出。

### 10.3 安全

- 離題、提示注入、醫療診斷、資料缺失、過期環境資料和嚴重症狀測試都有預期結果。
- App／Web bundle、repository 與 log 找不到真實 secret。
- Demo 使用虛構人物與測試資料，不出現學生真實個資。

### 10.4 穩定性

- 外部 API、量界智算任一失敗時 UI 不崩潰。
- 線上與離線示範狀態可明確分辨。
- 關鍵頁面在決賽設備、瀏覽器與網路條件完成事前演練。

## 11. P1 與延後項目

完成 P0 且所有驗收通過後才考慮：

- 推播提醒。
- 明日活動與短期預報。
- 正式登入、跨裝置帳號、同步、資料匯出與雲端刪除流程。
- 長期個人趨勢，但仍只描述關聯，不宣稱醫療因果。
- 具可信 provider 的即時路線比較、完整內嵌導航、班級統計、Line Bot、學校或健康中心整合。
- 有足夠合法資料後才評估專門的預測模型。

## 12. 成功定義

評審應在 30 秒內理解：

> AirMe 的主角不是 AQI 圖表，而是能把特定個人的活動與真實環境轉成有依據行動的 AI。

完整 Demo 後，評審應能回答：AI 看了什麼、做了什麼一般儀表板做不到的判斷、為什麼得到這個結果、如何不跑題，以及哪一段真的在 Coolify 與量界智算運作。
